# Treehouse design notes

Maintainer reference for the invariants behind treehouse's pool, lifecycle, VCS, and release machinery.
User-facing behavior lives in the [README](../README.md); contribution setup lives in [CONTRIBUTING.md](../CONTRIBUTING.md).
Each entry records why the code is shaped the way it is, so read the relevant one before changing that area.

## Pool and lifecycle invariants

- No daemon - all operations are inline CLI commands
- APFS sharing is default-off and fresh-Git-slot-only (`apfs_sharing`, `config.ResolveAPFSSharing`; [README](../README.md#apfs-copy-on-write-sharing)). The pool calls `vcs.ShareWorktreeFiles` only in fresh allocation, after seeding/optional branch and while the provisional lease and state lock still protect an unpublished slot; reuse and return never call it. Fatal mutation/cancellation/cleanup errors preserve quarantine, whereas a safe unsupported file/platform keeps Git's ordinary copy. `gitvcs/sharing.go` refuses setup with executable checkout/reference hooks, custom fsmonitor hooks, or filter attributes because Git has already run them before our insertion point; this is intentionally conservative, including LFS. Leases and stat checks do not exclude external file writers, so the opt-in retains that caller precondition. `internal/fileclone` owns no-follow descriptor traversal, staged native clones, metadata/hash verification and allocation metrics; Darwin `getattrlist` uses `FSOPT_PACK_INVAL_ATTRS` so absent ACLs cannot shift the packed offsets. An unreported security attribute is absent only when its reference length is zero; its offset then has no meaning. Other platforms return before enumeration. Diagnostics are stderr-only and distinguish logical payload from destination APFS private-data reduction, never volume-free-space claims. SIGKILL can leave staging, but cannot clear the already-persisted provisional lease.
- Git worktrees use detached HEAD by default and reset to whichever of the local or origin default branch is further ahead (prefers origin on divergence); opt-in branch creation is described in [README: Base branch](../README.md#base-branch).
- Acquire reuses a slot only when it belongs to the requesting clone (pools are keyed by origin URL, so two clones share one; `acquisitionCommonGitDir` stats the `vcs.CommonGitDir` of requester and candidate and compares them with `os.SameFile`, never as path strings, so neither a symlink alias nor letter case on a case-insensitive filesystem splits one clone, and an unresolvable identity on either side - including every non-colocated jj workspace - means skip, never match, while fresh allocation up to `max_trees` still proceeds), is idle, unleased, clean, and HEAD is merged into that exact reset target (resolved once to an immutable commit so the guard and `ResetWorktreeToRef` cannot disagree) or into the base the slot itself records (`headMergedIntoRecordedBase`, which re-reads HEAD and fails closed on a mismatch or any error, then still resets through the requested base's resolved commit); an inferred acquisition and a state entry predating `base_branch` both record none, so the repository default stands in as its implicit base HERE ONLY - acquire may reset such a slot because its HEAD stays reachable from a local branch, while prune and destroy deliberately do NOT give it that second reading, because they delete and so stay on the origin-validated default ref; it records HEAD at check time, re-reads it under a lock concurrent git/jj writes cannot bypass (git `HEAD.lock`; jj a single `rebase`/`abandon` revset of `@ & commit_id(expected)`), and re-checks dirtiness under that lock before any destructive tree update so uncommitted file or index changes after the first dirty check are not overwritten. It skips the slot if the lock cannot be taken, HEAD changed, or the tree became dirty, and fails closed when dirty, unverifiable, or merge state cannot be proven. `return` still discards dirty trees (`requireClean=false`)
- The branch worktrees are cut from is opt-in configurable: `base_branch` in `treehouse.toml` (repo-level wins over user-level) and `treehouse get --base <branch>` per invocation, flag over config, both empty keeping today's inference. `pool.resolveBaseBranch` is the single resolution point, called AFTER the fetch so a branch that exists only on origin resolves, and its result feeds both `AddWorktree` (new slot) and `IsWorktreeSafeToReset`/`ResetWorktreeToRef` (recycled slot). Only an explicit request is verified, through `vcs.VerifyBaseBranch` → `gitvcs.BranchExists`, which matches `refs/heads/<b>` or `refs/remotes/origin/<b>` - the same two refs `branchRef` chooses between - so branch names only, never tags/SHAs/`origin/<b>`, and never the literal `HEAD` (rejected by name, because `git clone` writes `refs/remotes/origin/HEAD`). Verification is mandatory rather than cosmetic: acquire SKIPS a slot whose safety check fails, so an unverified typo would present as a pool with nothing reusable and burn a fresh slot per call instead of reporting the typo. `VerifyBaseBranch` deliberately sits outside the `Backend` interface and refuses non-git backends: the jj path is plausibly fine but was never exercised, and a `Backend` method would put an unverified implementation on the destructive path. `gitvcs.branchRef` returns FULLY QUALIFIED refs: a bare name lets git rank `refs/tags/<b>` above `refs/heads/<b>`, silently cutting the slot from a same-named tag. `WorktreeEntry.BaseBranch` records ONLY an explicitly requested base, never an inferred default: prune and destroy give a slot a second reading against that field, so recording an inferred default there would widen what they delete for pools that never opted in. `ReleaseConditional` parks returned slots on the base they were cut from, resolved as caller-supplied (the CONFIGURED base, never the invocation's `--base`, because parking is about what the next acquire can recycle) → `WorktreeEntry.BaseBranch` recorded at acquire → repository default, and it clears the field when a slot parks on the default; without the recorded fallback a pool driven only by `--base` parks every slot on the default, recycles none, and grows to `max_trees` before reporting slots `status` shows as available. The default is resolved before the state lock so its failure surfaces before `beforeReset` kills processes, but it is only fatal when there is no requested base; if the reset on the requested base fails (branch deleted after verification) release warns and parks on the default rather than stranding the reservation. `LeaseInfo.BaseBranch` reports the resolved base for every acquisition (`get --lease --json`); `lease <name>` resolves it BEST-EFFORT through the slot's own `vcs.DefaultBranchForWorktree` and reports it empty when unresolvable, because that verb needs no branch and must never refuse to protect a home over a reporting field. `status` prints the base as a human line only - `status --json` is a top-level array and must stay one. One base per slot is a SHARED invariant: acquire, parking, prune, and destroy all judge a slot against the base it was cut from. `pool.headLandedOnItsBase` gives a slot the default ref reports unmerged a second reading against `WorktreeEntry.BaseBranch` (via `vcs.BaseBranchMergeRef` → `gitvcs.BranchMergeRef`, git-only for the same reason as `VerifyBaseBranch`); without it a `base_branch = "develop"` pool has every pristine slot labelled unlanded and neither `prune --yes` nor `destroy --all --yes` can ever reclaim it. It applies only to a slot carrying an EXPLICIT base (an empty field returns immediately), which is what keeps non-opt-in pools on exactly today's deletion semantics, and it runs only AFTER the default-ref check returned a definitive "not merged", so an unverifiable slot keeps that check's fail-closed classification
- The worktree's own directory leaf is opt-in unique: `unique_leaf` in config, `TREEHOUSE_UNIQUE_LEAF`, or `treehouse get --unique-leaf`, resolved by `config.ResolveUniqueLeaf` (see `treehouse.toml.example` for the setting and its precedence). It is read ONLY when a slot is created; reuse hands back the path already recorded in state, so both layouts coexist in one pool and enabling it never moves or renames an existing worktree. `internal/pool/state.go` remains the sole authority for where a slot lives
- Where a NEW slot is created is opt-in configurable: `worktree_path` in `treehouse.toml`, `TREEHOUSE_WORKTREE_PATH`, and `treehouse get --worktree-path`, in `root`'s precedence. `internal/pool/worktree_path.go` owns the placeholder vocabulary and every rule a template must satisfy; `treehouse.toml.example` documents the setting. What no single file shows: unset keeps the built-in `{pool}/{slot}/{repo}` path byte for byte; the template is read only when a slot is CREATED, so `WorktreeEntry.Path` stays the sole authority for where a slot lives and no existing worktree moves; validation and placement both run before the reuse loop, so a recycling acquisition rejects a bad template too; placement is judged on canonicalized paths while state records the REQUESTED spelling, so anything comparing the two must canonicalize both sides (`removableWorktreeContainer` does, and removes a parent only when it is a pool-owned slot directory); and `cmd.resolveReturnPoolDir` must confirm `pool.IsPoolDir` before trusting the two-levels-up guess. A template SUPERSEDES `unique_leaf`, because it names every segment including the leaf (`resolveWorktreePath` takes both and applies `unique_leaf` only to the built-in layout); setting both warns once rather than silently picking one. An existing directory is NEVER adopted, so `pool.freeTemplatedSlot` advances through candidate slot names (up to `max_trees` of them) until one resolves to a free path, warning on stderr per skip, and fails only when every candidate is occupied; refusing the first name instead would let a stray out-of-pool worktree - what a lost state file leaves behind, since recovery scans the pool directory only - make every later `get` fail.
- In-use detection uses process scanning plus short-lived persisted owner reservations for lifecycle operations. `status` (`pool.List`) reports the set `return` terminates - the scan minus the caller and its ancestors, as `process.UnprotectedProcessesInWorktree` computes it for `return` - and NOT the raw scan, which run from inside a pooled worktree answers with the caller's own process tree and so displayed processes `return` would never act on. It runs the scan and the caller/ancestor filter (`process.DropProtectedProcesses`) as two steps so the two failure modes stay distinguishable: a failed ancestry walk keeps the raw scan, because a slot that could not be verified must not read as quiet, while a failed process-table read has no list to fall back on: the slot is reported `StatusUnverified` (`unverified`, the machine-readable half, in both the table and `status --json`) with an empty process list, and the error is warned loudly on stderr (the diagnostic half). Unverified stands in only for what the process list would have decided (in-use, or its absence: damaged, dirty, available); leased, a live owner reservation, and "you're here" are known without a scan and still outrank it. `StatusHere` is therefore read from the caller's cwd alone: it used to be inferred from the caller's own shell turning up in the scan, which is the entry that is now filtered out. That comparison is the same containment test the scan applies to every process cwd (`process.WorktreeContainsCwd`) and resolves symlinks on both sides, because state records the pool path as configured while a shell reports its physical cwd: unresolved, a symlink-rooted slot reads available to the operator standing in it. The detached update-check child (`updater.backgroundCheckCommand`) runs from its own directory rather than inheriting the caller's, so treehouse never manufactures a process inside the slot it reports on. `return`'s own filter is deliberately unchanged: it protects the caller and its ancestors but not, say, a process-group peer, because a non-job-control shell puts background workers in the caller's own group and sparing them would leave live writers inside a slot being reset. `status` also reports each slot's checked-out branch as a three-outcome contract (`Branch`/`Detached`/`BranchErr`, so a read failure is never mistaken for a detached HEAD); only a marker-matching slot is read, so a markerless (damaged) slot never inherits the branch of a repository enclosing the pool, and jj slots report an empty branch
- Durable leases are a separate, process-independent reservation: `WorktreeEntry.Leased`/`LeaseID`/`LeaseHolder`/`LeasedAt` persist in the state file with `omitempty`. Every acquisition generates a new immutable 128-bit random `LeaseID`; older state without it loads with an empty ID and remains releasable through the legacy unconditional path. A lease is NOT derived from live processes, so it survives with zero processes inside the worktree and `healState` never clears it. Leased worktrees are skipped by `Acquire` and `prune`, classified `DestroyLeased` by destroy (removable only when the exact path is named with `--include-leased`, NEVER via `--all`), surfaced by `status` as `StatusLeased`, and cleared by `Release` (`return`), except for proven-safe recovered leases (see recovery below). `treehouse lease <name>` (`pool.LeaseExisting`) stamps that same lease state onto an EXISTING registered slot, state-only (no reset/fetch/clean/checkout; it reuses `markAcquired` and `leaseInfoFromEntry`, heals state first like every other state-mutating path so a name whose directory is gone is refused rather than stamped, and refuses unknown names, `Destroying` slots, and already-leased targets, writing no state on a refusal), because `get --lease` protects only a slot it allocates itself. Because it is applied to LIVE homes, it clears the acquiring session's owner reservation, so `get` gates its exit-time return on `ReleasePreconditions.RequireOwnedByCaller` (`ErrOwnerPreconditionFailed`): a slot re-reserved since acquisition is left exactly as found - no detach, no dirty prompt, no reset, no lease clear - and reported on stderr with which of the four states it hit (durably leased, already released, reserved by another session, or own identity unreadable - the lease path zeroes the owner fields too, so `Leased` must be tested FIRST or the protected home reads as discarded), because `return` run from INSIDE the subshell parks the slot and zeroes `OwnerPID` without killing its protected ancestors, so "someone else has it" would be a false reason. The detach runs as that check's `guarded` action, INSIDE the same `ValidateReleasePreconditions` state lock rather than after it: checking and then detaching are otherwise two instants, and a `lease` landing between them moves the HEAD of the very home the fresh lease exists to protect. `return <path>` stays the single release path and remains unconditional by default
- `destroy` is safe-by-default and mirrors `prune`: dry-run unless `--yes`, narrow explicit targets (`destroy <path>` for one worktree; `destroy <pool> --all` for that pool only - there is NO cross-pool/global destroy, and `--all` with no pool target is an error). The old blunt `--force` flag is REMOVED (this was the v2.0.0 breaking change); each risk class is its own opt-in: `--include-unlanded` (dirty, unmerged, or unverified), `--include-in-use` (running process or owner reservation; processes terminated cleanly first), `--include-leased` (leased, single named path only). A bare `--all --yes` removes only the disposable set (merged, clean, idle, unleased) and skips the rest with the flag that would include each. Bulk skips exit 0; a single-target skip exits non-zero. Entry points: `pool.DestroyWorktree` (single path, `allowLeased=true`) and `pool.DestroyPool` (bulk, `allowLeased=false`). Both share `classifyForDestroy` in `internal/pool/destroy.go`, which reuses prune's classification primitives (`ownerAlive`, `process.FindProcessesInWorktree`, `backingRepositoryMissing`, `vcs.IsDirty`, `vcs.IsHeadMergedIntoRef` against the `resolvePruneDefaultRef` ref) so destroy and prune agree on leased/in-use/unlanded/unverified/disposable. Removal keeps the same two-phase reservation as prune (reserve under flock, run `pre_destroy` hooks, remove only worktrees whose `sameDestroyReservation` still holds), so a worktree re-acquired during its hook is never deleted
- `return` takes a worktree PATH or a slot NAME, and resolves the argument as a path FIRST (`cmd.resolveReturnTarget`): the name reading is reached only where the path reading already found no managed worktree, so every argument that resolved before keeps resolving to exactly the same worktree. The two vocabularies genuinely collide - standing in a pool directory, `1` is both a slot name and a real subdirectory - and a working path must never be redirected. `cmd.couldBeWorktreeName` refuses anything holding a path separator (`/` and a backslash on every platform, plus absolute paths, `.` and `..`), so a path-shaped argument keeps reporting the path diagnosis instead of a misleading "no worktree named". A name is resolved through `pool.FindByName` against the pool of the repository the caller stands in (`cmd.repositoryPoolDir`), the same repository-scoped contract `lease <name>` and `enter <name>` have, because a name means nothing outside the pool that issued it; a path still finds its own pool and still works from outside the repository. The name is the slot's own identity, not a position in any listing, which is exactly why it is safe to accept: it does not move when another slot is created or destroyed
- `return --all` (`cmd.returnHeldWorktrees`) returns every HELD worktree in the caller's repository pool (`cmd.returnableStatus`): everything except `StatusAvailable`, `StatusDamaged`, and a `StatusHere` slot flagged `WorktreeStatus.HeldOnlyByCwd`. Available has nothing to return. Damaged is excluded because its marker is missing or unreadable, so neither the detach nor the reset a return performs can be judged safe, and `destroy` - which `status` already spells out for such a slot - is the verb that removes it. `HeldOnlyByCwd` exists because `StatusHere` HIDES whichever classification the slot would otherwise carry, so the status string alone cannot say whether anyone holds it: `pool.List` therefore classifies WITHOUT the cwd and lays `StatusHere` over the answer (leased and a live owner reservation still outrank it, and it still outranks unverified, in-use-by-process and dirty), setting the flag only when the hidden answer was `StatusAvailable`. `StatusDamaged` is the one classification the overlay does NOT cover: a missing marker says the slot's contents cannot be judged at all, standing in it does not make it readable, and letting the overlay erase it put the slot back in `--all`'s target set against the exclusion every doc states unconditionally. The recovery-scan case already re-forced damaged over the overlay, so the two now agree. Standing in a parked, clean, quiet slot is not holding it, and `enter` promises to leave pool state untouched, so resetting it - and counting it as a held worktree returned - would break that promise; stand in a leased, dirty, or busy slot and `--all` returns it like any other. Re-deriving dirtiness and process state in `cmd` would duplicate `List` and could disagree with it, which is why the fact is reported rather than recomputed. Naming a damaged slot, or the slot you stand in, explicitly still returns it, because the narrow target is a deliberate act while the bulk one must not surprise. The target set is deliberately WIDER than the other bulk verbs - prune skips a leased slot and destroy needs `--include-leased` on a named path - because a return leaves the slot in the pool and reclaiming a pool whose agents are gone is the point of the verb. Every target goes through the same `cmd.releaseWorktree` a named return uses, so the dirty confirmation is not skipped in bulk, and a per-worktree abort, skip, or failure never stops the ones after it: giving up on the first dirty slot would leave the rest held with no indication which. Two outcomes are SKIPPED rather than failed, because nothing went wrong and a retry would report them forever: a slot whose LEASE is no longer the one the listing saw (`pool.ErrLeasePreconditionFailed` - taken over OR simply returned in the meantime, which is why the message reports only that the slot is no longer the acquisition the run listed and never names a cause) and a recovered entry (`pool.RecoveredLeaseHolder`, which a state version bump or rotated key makes of a WHOLE pool at once and which every entry with an unknown seed inventory carries), which remains quarantined after the automatic recovery check and is never a target: its safety was not proven, so the run counts it held and skipped and prints the `return <path>` command that releases it. Every bulk release also carries `ReleasePreconditions.RefuseRecovered`, judged under the release's state lock, so an entry recovered AFTER the listing (a state key invalidated while the run waits on a confirmation) is skipped the same way (`pool.ErrRecoveredEntry`) instead of released. `cmd.bulkReturnPreconditions` is what makes the first detectable: the listing and the release are separated by every earlier confirmation in the run, so each release carries the lease `pool.List` observed - `ExpectedLeaseID` for a leased slot, `RequireUnleased` for every other held slot, and only `RefuseRecovered` for a leased slot whose ID is empty, which offers no lease to compare. Those two are SEPARATE fields on purpose: "still exactly this acquisition" and "still nobody's" are opposite predicates, and one field carrying both (an empty `ExpectedLeaseID` meaning "no lease") reads correctly and behaves oppositely the day a caller passes an identity variable that happens to be empty. `ReleasePreconditions.check` rejects an empty `ExpectedLeaseID` and the two combined with `pool.ErrInvalidReleasePreconditions`, which describes the CALL, not the worktree, so `--all` reports it as a failure rather than one of its skips. That is the WHOLE guarantee and the docs must not promise more: `ReleasePreconditions` cannot express "still the same owner reservation I observed" (`RequireOwnedByCaller` means owned by the CALLER, a different question), so a slot handed to another plain `get` is still unleased, passes, and is reclaimed - which is what `--all` does to in-use slots by design. The lease/owner checks live in `pool.releasableWorktree`, the ONE gate both `ValidateReleasePreconditions` and `ReleaseConditional` go through, so `releaseWorktree` can run them BEFORE the dirty confirmation and never offer to discard changes it would then refuse to discard. The run's exit status is the most urgent outcome, failure over abort over skip, because a failure is worth retrying and a deliberately-dirty slot is not. `--all` refuses a positional target and refuses `--if-lease-id`/`--if-lease-holder`, which identify ONE acquisition and cannot describe a set
- Exit statuses are mapped in `cmd/exit.go`: any error out of `Execute` is `ExitFailure` (1) unless a command tagged it with `withExitCode`. `return`'s aborts and `get`'s exit-time dirty bail-out both tag `ExitNotReturned` (3) so a caller can tell "dirty, slot unreclaimable" from a genuine failure - both left the slot as found while reporting success, which silently starved pools under automation. A command that leaves the world unchanged must never exit 0, with TWO deliberate exceptions, both of the same shape - the slot was never this run's to return: `get` exiting on `ErrOwnerPreconditionFailed` (another session durably leased it), and a `return --all` run in which every held slot was SKIPPED (`ErrLeasePreconditionFailed`, `ErrRecoveredEntry`, or a recovered entry), which prints "Returned 0 of N" and exits 0 because nothing it listed was still the acquisition it listed, or none of them could be released at all. Neither is a leak, and failing them would make a quarantined pool exit non-zero on every retry forever. 2 stays free for usage errors
- `get --lease` (see `getLeaseRunE`) is the non-interactive acquire: it opens no subshell, routes hook output and banners to stderr, and keeps path-only stdout unchanged. `get --lease --json` returns `pool.AcquireLeaseInfo`, and `status --json` exposes the same `lease_id`, holder, and timestamp. Conditional return uses `pool.ReleaseConditional` with `--if-lease-id` and optional `--if-lease-holder`; comparison, caller-side preparation, reset, and final clear share one `WithStateLock`, while return without conditions keeps the legacy path-only behavior
- Dirty checks include untracked files even when repository config hides them from normal `git status` output
- Prune deletes only idle managed worktrees that are clean and whose HEAD is merged into the default branch or the slot's recorded explicit base branch; dry run is the default
- Prune reports unsafe idle worktrees in grouped, stable categories and keeps raw VCS diagnostics for verbose output instead of default output
- Prune treats backing-repository-missing linked worktrees as orphans in both flavors (a git `.git` gitdir pointer or a jj `.jj/repo` store pointer naming a deleted directory; a `.jj/repo` directory is a main workspace and never an orphan); they are only deletable with explicit `--prune-orphans --yes`, and each candidate warns that content could not be verified
- Prune never treats an unreachable origin as a deletable orphan; those worktrees stay skipped because the repository may still be valid. Each backend owns its unreachable-origin error vocabulary (`gitvcs`/`jjvcs` `IsOriginAccessError`; jj shells out to git so its patterns wrap git's), and the `vcs` facade classifies by error content, not by the configured backend
- Global prune enumerates managed pool directories under the user-level treehouse root. Every prune and destroy (repo-scoped too) derives each worktree's owning repository from that worktree's own VCS metadata (`resolvePoolRepoRoot`, `worktreePruneContextResolver`), never from the current directory or one pool-wide root: a shared pool holds slots from several clones, and one clone's root makes git refuse the other's removal
- Global prune loads user-level config and hooks only because it can run without a repository context
- State file tracks pool membership, temporary owner/destroy reservations, and explicit durable leases.
  It still does not infer long-term usage from processes.
- `WriteState` is atomic: it writes to a temp file in the pool directory, fsyncs it, commits it with the platform replacement primitive, and syncs the parent directory where supported.
  A crash mid-write can never leave a truncated or empty state file.
  `ReadState` treats a state file that exists but fails to parse (empty or truncated) as recoverable rather than a hard failure: it prints a loud warning to stderr and rebuilds a `State` by scanning the pool directory for worktree subdirectories still on disk (`recoverCorruptState` in `internal/pool/state.go`).
  Since the real reservation (owner vs. lease vs. idle) is unknowable from disk alone, and recovery cannot reconstruct a trusted seed inventory, every recovered entry is marked `Leased` with a `RecoveredLeaseHolder` placeholder and `SeedInventoryKnown=false`.
  Every pool operation first runs `recoverQuarantinedEntries` under the state lock (`WithStateLock`), so whichever command runs next - `return <path>` included - attempts to auto-free recovered Git entries, but only those proven process-free (the caller and its ancestors count, so a shell standing in the slot keeps it), tracked-clean including submodule contents (whatever `submodule.<name>.ignore` says), and with HEAD contained in a remote-tracking ref or the recorded/inferred base. Untracked-only files are moved by rename into the slot's one retained backup folder beside the pool (`recoveryBackupDir`: `treehouse-recovered-backup-<pool>-<slot>` in the pool's parent directory, derived from the pool and slot name rather than recorded, so every retry reuses it, a name an earlier attempt took gets a numeric suffix instead of being overwritten, and `status` reports the folder while it is non-empty; a backup folder or destination folder inside it that is a symlink is refused, so a move never lands outside it; on Unix the backup folder is kept owner-only (`0700`), tightened when the current user owns it and refused otherwise; on Windows, where ACL handling is out of scope, untracked files are never moved and such a slot stays leased) before the lease is cleared and an empty trusted seed inventory is recorded, the same transition a named return makes, so the freed entry is not re-quarantined. Every uncertain or unsafe entry stays leased; `status` gives its precise reason (persisted as `RecoveryReason`, cleared whenever the lease is) and advises inspection followed by named `return <path>`, including for a recovered entry it reports damaged. `return --all` still skips entries that remain recovered, and `destroy` removes one only via a named `--include-leased` target. Recovery cannot reconstruct the seeded ignored-file inventory, which is not included in the untracked backup and may remain when reused; this limitation is unchanged.
  README's "Recovering missing pool state" section owns the user-facing recovery procedure
- Seeding behavior is documented in [README: Seeding gitignored files](../README.md#seeding-gitignored-files). Inventories are HMAC-authenticated in pool state (not the mutable worktree); untrusted or unknown inventories fail closed and quarantine rather than silently recycle. Seeded cleanup is rooted/symlink-safe; jj cleanup stays authenticated
- Pre-3.0 state is adopted, not quarantined: no release before 3.0 seeded ignored files, and every 3.0+ write creates `treehouse-state.key` before it records an inventory, so unversioned state is adopted with an empty inventory. That includes unversioned state BESIDE a key: a 2.x binary still running across the upgrade rewrites 3.0 state without its version and seed fields (issue #151), and quarantining that rewrite would take the whole pool out of service again. Known limitation: any ignored files 3.0 seeded before such a rewrite are no longer recorded, so they are not cleaned up and stay in the worktree when the slot is reused. treehouse 3.0.0 got this wrong and quarantined every pre-3.0 entry as `RecoveredLeaseHolder`. Those entries are deliberately NOT told apart from genuine recoveries: 3.0.0 overwrote every holder, a pre-2.1 lease has no lease ID, and lease times and the key's mtime cannot prove a slot was idle or when the key was written, so any inference could revoke a durable lease. They use the recovered-entry policy above, for Git and jj alike.
- All VCS operations go through the `internal/vcs` seam (`vcs.Backend`, 22 operations); backends shell out to the `git`/`jj` binaries (go-git has incomplete worktree support). Git is the default backend everywhere, including colocated (`.jj`+`.git`) and `.jj`-only repos; jj is a strict opt-in via `vcs = "jj"` in config or `TREEHOUSE_VCS=jj` (precedence: env, repo `treehouse.toml`, user config), effective only where a `.jj` directory exists; an unrecognized `vcs` value is ignored (git default kept) with one deduped stderr warning naming the value and its source. Pooled jj workspaces are `.jj`-only and cannot carry an untracked config file, so `backendFor` resolves their opt-in by reading the `.jj/repo` pointer and checking config at the main repository root - file inspection only, never backend selection from a marker. Per-worktree facts and actions, however, dispatch on the slot's own marker (`slotMarkerBackend`: a `.git` entry wins, then a `.jj` directory): `backendForWorktree` routes `IsDirty`, `IsHeadMergedIntoRef` (with its ref from `DefaultBranchMergeRefForWorktree`), `ResetWorktree`, `ResetWorktreeToRef`, `IsWorktreeSafeToReset`, `DetachWorktree`, `FindMainRepoRootFrom`, and release-time root/branch discovery (`DefaultBranchForWorktree`), and `backendForRemoval` routes `RemoveWorktree`/`RemoveCleanWorktree` the same way, falling back to `backendFor(repoRoot)` when the path is missing so error surfacing is unchanged. This is artifact-typed dispatch of operations on an existing slot, NOT marker-based opt-in - ordinary directories without a marker and worktree creation still follow the configured backend - so the configured backend never answers for a slot of the other flavor (a `.jj`-only slot read through git would resolve the repository enclosing the pool and report its facts, misclassifying dirty work as disposable). Acquire is flavor-aware too: `get` reuses only marker-matching slots and creates new ones with the selected backend; other-flavor slots stay untouched, are surfaced by `status` (`WorktreeStatus.Flavor`), count toward `max_trees`, and are migrated via `destroy` + re-`get`. A markerless (damaged) slot fails closed everywhere: acquire never reuses it, `return` clears its lease without reading its dirtiness (so it never prompts to discard changes it would not touch) and without branch discovery, reset, or detach, `status` reports it `damaged` without reading its facts, `lease` still stamps it (an operator may need to protect a damaged home) but reports its base empty instead of resolving through the fallback, prune classifies it cannot-verify without reading facts through the fallback, and destroy classifies it unverified and removes it (plain-directory route; stale registrations self-heal at the next add) only with `--include-unlanded`; as defense in depth the destructive `vcs` wrappers (`ResetWorktree`, `ResetWorktreeToRef`, `ResetWorktreeWithSeededPaths`, `ResetWorktreeToRefWithSeededPaths`, `DetachWorktree`) refuse markerless paths outright
- jj backend semantics: dirty means the working-copy commit `@` is non-empty or described; reset is `jj abandon -r @` then `jj new <default>` (recoverable via `jj op restore`); merged-detection is the ancestry revset `@- & ~::<ref>` being empty, so squash-merged work deliberately reads unmerged (fail-safe); default branch resolution prefers origin bookmarks `main`/`master`/`trunk` and never uses bare `trunk()` (it falls back to `root()` without remotes); the workspace store pointer is rewritten to a canonicalized absolute path and canonicalized again on both read routes, so a repository reached through a symlinked path resolves to one pool identity; `PruneWorktrees` is a documented no-op with self-healing at add time; as defense in depth, `RemoveWorktree` refuses to delete an existing directory that is not a jj workspace or that is the main workspace (its `.jj/repo` is the store itself, not a pointer file), so even a misrouted call cannot silently delete git-owned files or the whole repository - an already-missing path still gets its stale workspace registration forgotten. jj tests isolate `JJ_CONFIG` (with `git.colocate=false`) and skip when `jj` is not on PATH, so CI without jj is unaffected
- The pool root is made self-ignoring (`.gitignore` containing `*` written inside it) because non-colocated jj repos never read `.git/info/exclude`; inside git repos the `info/exclude` entry is still added too (`config.EnsureExcluded`)
- Self-healing: stale state entries are auto-removed, and `get` prunes stale worktree registrations before adding a worktree (the git backend via `git worktree prune`; the jj backend by forgetting a stale same-path workspace registration at add time)

## Contribution gate and release CI

- PRs to `main` must carry the no-mistakes pipeline signature and a v1 pipeline step attestation whose `head_sha` matches the current PR head (`review`, `test`, and `document` each `status=completed`). Signature-only bodies from no-mistakes older than 1.46.0 fail. The required check is `PR must be raised via no-mistakes` (`.github/workflows/no-mistakes-required.yml`), enforced by the repository `main` ruleset; only the owner/Admin role can bypass it.
- The required check is decided by the SHARED composite action `kunchenguid/no-mistakes/.github/actions/require-no-mistakes`, pinned to an immutable commit (never `@main`, which the judged PR could edit). Bot exemptions ride as its `exempt-authors` input, deliberately not a job-level `if:`: a skipped job never reports a required context, so the PR would block on a status that can never arrive. Bumping the pin is a separate, deliberate PR.
- `.github/scripts/no-mistakes-gate.sh` survives for ONE consumer: `release.yml`'s `release-pr-gate-status` job (see the next bullet). Its structural release-please test is therefore still load-bearing, not dead code, and `TestNoMistakesGateDecisions` drives the script directly.
- release-please opens its PRs with `GITHUB_TOKEN`, so GitHub creates **no** workflow runs on them and the gate can never report there. `release.yml`'s `release-pr-gate-status` job publishes the required context on the release PR head by running that same gate script, so release PRs go green without an owner override.
- A workflow backing a required check must never use `paths`/`paths-ignore`: a filtered required check never reports and blocks the PR forever. `TestPullRequestWorkflowsExcludeReleasePleaseOutputs` encodes both that rule and the opposite rule for ordinary PR workflows.
